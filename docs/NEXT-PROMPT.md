# Prochaine étape — validation réelle et préparation du déploiement Mazlove

Tu interviens sur Julien-RDS/Mazlove, depuis le dernier master. Lis `docs/TRACKING-PHASE4.md`, `docs/PRODUCTION.md`, `docs/TRACKING.md` et les fichiers concernés. Préserve le design et les parcours existants. Ne lance ni Docker ni déploiement sans instruction explicite. Aucun service payant, nouvelle clé, Stripe, application native ou infrastructure multi-instance. Avance par étapes courtes ; pas d’audit général.

La phase 4 apporte le GPS global, la reprise après rechargement, un verrou Web Locks avec prise de relais entre onglets, un endpoint serveur borné pour la séance active, des verrous sur le cycle de séance, des publications après commit, l’expiration STOMP, des emails SOS durables avec reprise bornée et des gardes prod. Les tests autonomes ne prouvent pas le fonctionnement de PostgreSQL/Redis/STOMP/SMTP réels.

1. Vérifie l’accès à une base **de test dédiée**, Redis, SMTP/MailHog et au backend/frontend de test déjà disponibles. Ne démarre pas Docker. S’ils sont absents, indique précisément le blocage et poursuis seulement le travail indépendant des services.
2. Exécute les tests `ActiveSessionIT`, `TrackingReliabilityIT`, `StompSecurityIT` avec les variables/commandes de TRACKING-PHASE4. Active aussi `MAZLOVE_MAIL_IT=true` si MailHog est accessible. Corrige les défauts réellement observés. Vérifie les historiques >50, les deux rôles, l’absence de séances tierces, les courses départ/rendez-vous et ingestion/arrivée/annulation, l’unicité EN_ROUTE, les TTL et la suppression de compte.
3. Exécute le parcours navigateur réel `tracking.spec.js` avec les fixtures versionnées : consentement, départ, accueil sans perte GPS, baisse ETA, coupure/reconnexion, deux pings d’arrivée, code, séance puis fin. Complète les contrôles réels de détour durable, perte/récupération du signal et révocation de partage si nécessaire ; les tests unitaires existants ne suffisent pas à certifier ces parcours.
4. Vérifie les emails SOS dans MailHog, les trois tentatives après refus certain, l’absence de doublon lors d’appuis répétés et la visibilité des échecs/incertitudes pour l’utilisateur et l’administrateur. Teste le redémarrage du worker après un envoi interrompu. Ne promets pas un « exactement une fois » avec SMTP : les résultats incertains doivent rester explicites et ne pas être relancés automatiquement.
5. Sur l’environnement de préproduction existant, vérifier HTTPS, origines WebSocket, expiration JWT en connexion ouverte, adresse client réelle derrière le proxy, quotas publics, absence de journaux contenant jetons/positions et absence de `/api/dev/*`. Répéter migration et rollback sur une copie de données avant toute production. Ne pas utiliser la configuration Compose dev comme configuration prod.
6. Vérifie Safari/iOS et Chrome/Android réels : permission GPS, Web Locks, Wake Lock, arrière-plan, mise en veille et reprise. Documente les comportements constatés. Sans Web Locks, le GPS échoue explicitement ; ne pas remplacer cela par un verrou localStorage sujet aux courses.
7. Préserve MapLibre à la demande, les requêtes sans chevauchement et la pause des rafraîchissements en arrière-plan. Mesure le build et les parcours réellement exécutés ; n’invente pas de score Lighthouse. Relance `mvn test`, `npm test`, `VITE_DEMO=false npm run build` et `npm run test:frontpage` après les changements.

Livre les corrections, tests et documents, puis un commit et un push sur master sans forcer l’historique. Termine avec les résultats exacts, les tests non exécutés, les limites encore présentes et le commit poussé. Toute autorisation de déploiement doit porter sur une version concrète déjà préparée et vérifiée.
